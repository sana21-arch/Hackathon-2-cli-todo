## Summary

Build a CLI-based in-memory todo system demonstrating spec-driven development with clean architecture. The system provides essential task management operations (add, list, update, delete, complete, search) through an intuitive command-line interface. Target audience: hackathon judges and beginner software engineers. Focus: clarity, simplicity with professionalism, and foundation for future evolution to web/persistence layers.

**Key Technical Decisions**:
- Python 3.13+ with dataclasses for Task model
- argparse for CLI parsing (stdlib, zero dependencies)
- In-memory list as task store (session-scoped)
- Three-layer architecture: CLI → Service → Model
- Sequential integer IDs with auto-increment

## Phase 0: Research & Design Decisions

### Research Questions

1. **CLI Framework Choice**: argparse (stdlib) vs typer (external library)
   - **Decision**: argparse
   - **Rationale**: Zero dependencies aligns with constitution "no unnecessary abstractions" and reproducibility principle. argparse sufficient for 7 commands with basic options.
   - **Alternatives Considered**: typer (better UX, type hints) - Rejected due to external dependency requirement

2. **Task ID Generation Strategy**: Auto-increment vs UUID
   - **Decision**: Auto-increment starting from 1
   - **Rationale**: Spec requirement FR-008 mandates "unique, sequential integer IDs starting from 1". Simple, predictable, user-friendly for CLI context.
   - **Alternatives Considered**: UUID - Rejected as over-engineering for in-memory single-user system

3. **Data Structure for Task Store**: List vs Dict
   - **Decision**: List with sequential access, IDs separate from list indices
   - **Rationale**: Supports deletion without ID gaps (FR-005). List preserves creation order (spec requirement for display ordering).
   - **Alternatives Considered**: Dict with ID keys - Rejected because deletion creates permanent ID gaps

4. **Task Model Implementation**: Dataclass vs Plain Class vs NamedTuple
   - **Decision**: Dataclass with type hints
   - **Rationale**: Constitution mandates dataclasses (Principle V). Provides immutability option, automatic __init__, __repr__, type hints support.
   - **Alternatives Considered**: Plain class (more boilerplate), NamedTuple (too restrictive for mutable fields)

5. **Error Handling Strategy**: Exceptions vs Return Codes
   - **Decision**: Exceptions for business logic errors, CLI layer catches and formats for stderr
   - **Rationale**: Pythonic approach. Separates concerns: service layer raises exceptions, CLI layer handles user-facing error messages.
   - **Alternatives Considered**: Return codes (less Pythonic, muddles business logic with error handling)

6. **Optional Fields (Priority, Timestamp)**: Include or Defer
   - **Decision**: Include `created` timestamp (spec mentions it in Key Entities), defer priority
   - **Rationale**: `created` field specified in spec.md line 130 for display ordering. Priority not mentioned in P1-P5 user stories, defer to Phase 2.
   - **Alternatives Considered**: Including priority now - Rejected per YAGNI principle

7. **Input Validation Approach**: Strict rejection vs Lenient acceptance
   - **Decision**: Strict rejection with actionable error messages
   - **Rationale**: Spec requires validation (FR-009, FR-010) and actionable errors (SC-004). Better UX to fail fast with clear guidance.
   - **Alternatives Considered**: Silent failure or lenient acceptance - Rejected as poor UX

### Design Decisions Summary

| Decision | Choice | Rationale |
|----------|--------|-----------|
| CLI Framework | argparse (stdlib) | Zero dependencies, sufficient for requirements |
| Task ID Strategy | Auto-increment from 1 | Spec requirement FR-008, user-friendly |
| Task Store | Python list | Preserves order, supports deletion without ID gaps |
| Task Model | Dataclass | Constitution requirement, type hints, clean syntax |
| Error Handling | Exceptions + CLI formatting | Pythonic, separates concerns |
| Optional Fields | Include `created`, defer priority | Spec mentions timestamp, priority not in P1-P5 |
| Validation | Strict with actionable errors | Spec requirements FR-009/FR-010, SC-004 |

### Data Model (data-model.md)

**Entity: Task**

| Field | Type | Required | Default | Validation | Description |
|-------|------|----------|---------|------------|-------------|
| id | int | Yes | Auto-assigned | > 0, unique | Sequential identifier starting from 1 |
| description | str | Yes | N/A | Non-empty, any printable chars | User-provided task text |
| completed | bool | Yes | False | N/A | Completion status flag |

**State Transitions**:
- New task → `completed=False`
- User completes → `completed=True`
- User marks incomplete → `completed=False`
- User deletes → Task removed from store

**Validation Rules**:
- Description MUST be non-empty string (FR-009)
- Description MAY contain any printable characters including quotes, newlines
- ID MUST exist in task store before operations (FR-010)
- ID MUST be positive integer

### Component Responsibilities

**CLI Layer** (`src/cli/`):
- Parse command-line arguments using argparse
- Dispatch to appropriate command handler
- Format success messages for stdout
- Format error messages for stderr
- Set exit codes (0 for success, 1 for error)
- Display help text

**Service Layer** (`src/services/task_service.py`):
- Manage in-memory task store (module-level list)
- Generate sequential task IDs (track next_id counter)
- Implement CRUD operations:
  - `add_task(description: str) -> Task`
  - `list_tasks() -> list[Task]`
  - `get_task(task_id: int) -> Task | None`
  - `update_task(task_id: int, description: str) -> Task`
  - `delete_task(task_id: int) -> Task`
  - `toggle_complete(task_id: int, completed: bool) -> Task`
  - `search_tasks(keyword: str) -> list[Task]`
- Validate inputs (non-empty descriptions, valid IDs)
- Raise exceptions for errors (TaskNotFoundError, ValidationError)

**Model Layer** (`src/models/task.py`):
- Define Task dataclass with type hints
- Fields: id (int), description (str), completed (bool), created (datetime)
- No business logic (data structure only)

```
User: todo add "Buy groceries"
  ↓
CLI Layer (main.py):
  - Parse args: command="add", description="Buy groceries"
  - Call: commands.add_command(description)
  ↓
CLI Commands (commands.py):
  - Call: task_service.add_task(description)
  ↓

```

```
Service Layer raises exception
  ↓
CLI Commands catches exception
  ↓
CLI Commands formats error message
  ↓
Print to stderr
  ↓
Return exit code 1
```

**Exception Types**:
- `TaskNotFoundError`: Raised when task ID doesn't exist
- `ValidationError`: Raised when input validation fails (empty description, empty keyword)

### In-Memory Data Handling

**Task Store Structure**:
```python
# Module-level in task_service.py
_task_store: list[Task] = []
_next_id: int = 1
```

**ID Generation**:
```python
def add_task(description: str) -> Task:
    global _next_id
    task = Task(id=_next_id, description=description,
                completed=False, created=datetime.now())
    _next_id += 1
    _task_store.append(task)
    return task
```

**ID Management After Deletion**:
- IDs are permanent, never reused
- Deletion removes from list but doesn't decrement _next_id
- Example: Add tasks 1, 2, 3 → Delete task 2 → Next add gets ID 4 (not 2)

**Lookup Strategy**:
```python
def get_task(task_id: int) -> Task | None:
    for task in _task_store:
        if task.id == task_id:
            return task
    return None
```

**Search Implementation**:
```python
def search_tasks(keyword: str) -> list[Task]:
    keyword_lower = keyword.lower()
    return [task for task in _task_store
            if keyword_lower in task.description.lower()]
```

### UX Consistency Rules

1. **Output Format**:
   - Success messages: `<Action> task #<id>: "<description>"`
   - List header: `ID | Status | Description` with separator `---|--------|------------`
   - Status indicators: `[ ]` for incomplete, `[✓]` for complete

2. **Error Messages**:
   - Always actionable: state problem + solution
   - Format: `Error: <problem>. <suggested action>`
   - Example: `Error: Task ID 5 not found. Use 'todo list' to see valid IDs.`

3. **Exit Codes**:
   - 0: Command succeeded
   - 1: Command failed (invalid input, task not found, etc.)

4. **Help Text**:
   - Available via `--help` or `-h` for main command and all subcommands
   - Format: usage line, description, examples
   - Consistent structure across all commands

5. **Input Validation**:
   - Validate before state changes (fail fast)
   - Non-empty strings for description/keyword
   - Positive integers for task IDs
   - Existence check before operations
